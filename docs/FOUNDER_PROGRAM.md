# Founder Program

Three limited, numbered, one-time-payment tiers — Founder First (300 seats, $50, 1 year
of Pro), Founder Gold (150 seats, $125, 3 years of Pro), Founder Black (20 seats,
$1,899, lifetime Pro + a physical kit). Public page at `/founders`; status in the
client panel's "Founder Status" tab; management in the admin panel's "Founder Program"
tab.

Unlike [Contributions](./CONTRIBUTIONS.md) (which never touch Pro at all), a Founder
purchase's headline benefit *is* Pro access — see "How Pro is granted" below for how
that's wired into the real entitlement system without breaking anyone's billing.

## Availability — the hard requirements

- `founder_tiers.total_quantity` / `sold_quantity` live only in the database — no
  frontend constant, no cache. `GET /api/founders/tiers` and the `/founders` page
  (a Server Component — reads the database directly, not through a client fetch on
  first paint) are both `force-dynamic`, and `json()` always sets `Cache-Control:
  no-store`.
- `remainingQuantity = totalQuantity - soldQuantity`, clamped to `>= 0`
  (`src/lib/founders.ts`).
- Sold-out tiers stay visible with a "Sold out" badge and a disabled CTA — never
  hidden. `isAlmostGone()` flips a tier's UI to "Almost gone" at ≤10% remaining.
- The frontend never decides "sold out" on its own — it renders exactly what
  `GET /api/founders/tiers` says, and re-fetches on load and after a cancelled/
  completed checkout.

## Founder number assignment — atomic, server-only

`tryAssignFounderNumber()` in `src/lib/founders.ts` is a single SQLite statement:

```sql
UPDATE founder_tiers SET sold_quantity = sold_quantity + 1, updated_at = ?
WHERE id = ? AND sold_quantity < total_quantity
```

If `changes === 0`, the tier is exactly full and no number is handed out — however
many settlement attempts race for the last slot (this codebase is a single, long-running
Node process with one shared synchronous `better-sqlite3` connection — see
`src/lib/db.ts` — so there is no cross-process race to guard against, only ordering
within one process, which SQLite's own transaction serializes). The number itself is
never generated by the client, never sent by the client, and never computed until a
Checkout Session has actually been confirmed paid by the webhook.

Formatting: `formatFounderNumber()` pads to the width of the tier's own
`total_quantity` — 3 digits for 300/150 (`#001`–`#300`, `#001`–`#150`), 2 digits for 20
(`#01`–`#20`). No separate "padding" column is stored; it's derived from
`total_quantity` at read time.

**The one unresolved edge case**: if Stripe confirms payment for a purchase in the
exact instant a tier's last slot is taken by a different purchase, the second buyer's
purchase is still marked `PAID` (they were charged — never leave someone paid-but-
untracked) but gets `founder_number = null` and logs a `console.error`. This needs a
human: either refund that purchase or raise the tier's limit by one. It has never been
observed in testing but is architecturally possible, so it's documented rather than
silently handled.

## How Pro is granted

`grantFounderPro()` lives in `src/lib/subscriptions.ts` (not in `founders.ts`) —
that file's own header comment calls it "the single source of truth for
subscription/Pro entitlement state," so this is the one place any Pro grant is allowed
to happen.

**The critical safety rule**: `subscriptions.user_id` is the table's `PRIMARY KEY` —
one row per user, no per-source rows. A naive upsert would silently overwrite an
active Stripe subscriber's `source: "STRIPE"` with `"MANUAL"`, which would hide their
"Manage subscription" button (`SubscriptionCard` only renders it for
`source === "STRIPE"`) even though Stripe is still actively billing them. So:

- If the user currently has an active **STRIPE or APPLE** subscription, `grantFounderPro`
  **never touches `source`** — it only extends `current_period_end` (lifetime always
  wins on either side; otherwise the later of the two dates wins). Every other column
  (customer id, provider subscription id, plan, auto-renew, …) is left exactly as is.
- Otherwise (no subscription, or an existing `MANUAL` grant from an earlier Founder
  purchase) it's safe to upsert a normal `source: "MANUAL"` row, still extending
  rather than shortening any existing window.
- Lifetime (`Founder Black`) is stored as `current_period_end = NULL`, which
  `subscriptionGrantsPro()` already treats as "never expires" — no new sentinel value
  was introduced.

See `tests/lib/subscriptions.test.ts` ("grantFounderPro") for the exact matrix this
covers, including the specific regression test for "an active Stripe subscriber buys a
Founder tier and keeps their billing portal access."

**Refunds do not automatically revoke Pro.** A full refund marks the purchase
`REFUNDED` (visible in the client panel and admin), but clawing back a merged
`current_period_end` would need to know how much of the user's *current* window came
from *this specific* purchase — which isn't tracked, and getting it wrong (revoking a
real Stripe subscriber's paid-for access) is worse than not automating it. Revoking
access after a Founder refund is a manual admin action for now.

## Checkout — `POST /api/founders/checkout`

Same shape as the existing `/api/checkout` (Pro subscriptions) rather than
Contributions' dynamic-`price_data` pattern, because **each tier has its own fixed
Stripe Price ID** (`STRIPE_FOUNDER_FIRST_PRICE_ID` etc.) — see `.env.example`.

The client sends `{ "tierSlug": "founder-first" }` and nothing else. The server:

1. Resolves the user from the Bearer token — never from the body.
2. Looks up the tier by slug; 400 if unknown.
3. 409 `tier_inactive` if the tier is off; 409 `sold_out` if `remainingQuantity <= 0`;
   503 `server_not_configured` if no Stripe Price ID is set for it.
4. 409 `already_owned` if the caller already has a `PAID` purchase of this exact tier
   (`getActiveFounderPurchase`).
5. Validates the Stripe Price itself (`stripe.prices.retrieve`), same defensive check
   `/api/checkout` already does.
6. Creates a `PENDING` row, then a `mode: "payment"` Checkout Session with
   `metadata: { kind: "founder", purchaseId, userId, tierSlug }` (mirrored onto
   `payment_intent_data.metadata`).
7. `success_url` → `/panel?tab=founder&founder=success&session_id={CHECKOUT_SESSION_ID}`,
   `cancel_url` → `/founders?checkout=cancelled`.

**Idempotency**: a still-open Checkout Session created for the same user+tier in the
last 10 minutes is reused instead of creating a second one (same pattern as
Contributions' `findRecentPendingContribution`), plus Stripe's own `idempotencyKey`
(scoped to `founder_<userId>_<Idempotency-Key header or purchase id>`).

**A confirmed purchase can never be created twice**: a partial unique index —

```sql
CREATE UNIQUE INDEX idx_founder_purchases_user_tier_active
  ON founder_purchases(user_id, founder_tier_id)
  WHERE payment_status IN ('PENDING', 'PAID')
```

— means at most one *active* purchase per (user, tier) at a time, while a `FAILED`/
`EXPIRED`/`REFUNDED` attempt frees the slot for a legitimate retry. This is enforced by
the database, not just application logic.

**The success redirect never activates anything.** `GET /api/founders/session/[id]`
(same "don't trust the URL" pattern as `/api/contributions/session/[id]`) is what the
client panel polls after returning from Stripe — it checks the local row's real status,
and only falls back to a live `stripe.checkout.sessions.retrieve()` + re-running the
same settlement function if the row is still `PENDING` (webhook not arrived yet).
Activation only ever happens in `settleFounderPurchaseFromSession()` — called from both
the webhook and this poll endpoint, so the cross-checks can't diverge between the two.

## Webhook — extends the existing `POST /api/webhook`

No new endpoint, no new event types beyond what Contributions already required (see
[`docs/STRIPE.md`](./STRIPE.md)) — Founder events are just more branches on the same
`metadata.kind` dispatch, this time `kind: "founder"`.

`settleFounderPurchaseFromSession()` (`src/lib/founders.ts`):

1. No-ops unless `metadata.kind === "founder"` and `payment_status === "paid"`.
2. No-ops if the local row isn't `PENDING` (idempotent replay).
3. Refuses (logs, leaves `PENDING`) on a user/amount/currency mismatch against the row
   created at checkout time — metadata is never trusted alone.
4. Inside one DB transaction: assigns the founder number (or leaves it `null` if the
   tier just sold out — see above) and marks `PAID`.
5. Outside the transaction (idempotent itself): computes `pro_starts_at`/`pro_ends_at`
   and calls `grantFounderPro()`.

`charge.succeeded` / `payment_intent.succeeded` / `payment_intent.payment_failed` /
`charge.refunded` all exclude known Founder payment intents from the subscription-refund
fallback logic — the exact same reasoning already documented for Contributions in
`docs/STRIPE.md`, just extended to a second one-time-payment source per customer.

## Data model

Four new tables, additive only (`CREATE TABLE IF NOT EXISTS`, same migration style as
every other table in `src/lib/db.ts` — no ORM, no separate migration framework):

- **`founder_tiers`** — one row per tier. `sold_quantity` only ever changes inside
  `tryAssignFounderNumber`'s transaction.
- **`founder_purchases`** — one row per purchase attempt (including failed/expired
  ones, for audit). Unique on `(founder_tier_id, founder_number)` (SQLite treats
  multiple `NULL`s as distinct, so many `PENDING` rows can coexist before numbering),
  unique on `stripe_checkout_session_id` and `stripe_payment_intent_id`, and the
  partial unique index on `(user_id, founder_tier_id)` described above.
- **`founder_profiles`** — one row per user, Founders Directory display name +
  directory/credits/case-study consent flags. Independent of any purchase — created
  lazily the first time a Founder saves a preference.
- **`founder_black_fulfillments`** — one row per Founder Black purchase, physical kit
  status (`card_status`/`certificate_status`/`letter_status`/`shirt_status`, each
  `pending → prepared → shipped`), shipping address, tracking number.

## Privacy

Shipping address and full name (`founder_black_fulfillments`) are returned by exactly
two endpoints: `GET /api/founders/me` (the owner reading their own data) and
`GET /api/admin/founders/purchases/[id]/kit` (an admin fulfilling that specific kit).
Neither the purchases list (`GET /api/admin/founders/purchases`) nor the CSV export
(`GET /api/admin/founders/export`) include it — both are deliberately limited to email,
tier, number, status, and dates.

## Founders Directory / credits / case studies

All three are opt-in, off by default, editable any time from the client panel
(`PATCH /api/founders/profile`). Nothing reads `consent_directory` yet to actually
render a public directory page — that's a follow-up; the consent model exists so it
can be added without a breaking schema change, and no name is ever shown anywhere
without the corresponding consent flag being true.

## Discord

**No real Discord role-assignment integration exists in this repo.** `bot/` is a
separate Discord bot (`beta_testers` email collection + owner DM notifications only,
see `bot/README.md`) — it has no mechanism to assign a server role to anyone, and no
link between a website `users.id` and a Discord user id at all. Per the brief for this
feature, no risky stopgap was built. Instead:

- `founder_purchases.discord_sync_status` (`pending` | `assigned` | `failed` |
  `removed`) exists and defaults to `pending` on every new purchase — visible in both
  the client panel and the admin purchases list.
- Nothing currently transitions it out of `pending`. A real integration would need,
  at minimum: a way for a user to link their Discord account (OAuth, or reusing the
  bot's existing `/beta` modal flow to capture a `discord_id` against the *authenticated*
  user rather than an anonymous beta signup), a bot command or admin action that calls
  `client.guilds.fetch(...).members.fetch(...).roles.add(...)` for the right role per
  tier, and a way to write the result back to `discord_sync_status` via a small
  internal API the bot process can call (mirroring how it already shares the SQLite
  database with the website).
- Until that exists, the admin panel is the only place this status can change, and
  only implicitly (it isn't editable yet) — this is intentionally left as a known gap
  rather than papered over.

## Language rules this implementation follows

Per the brief, benefit copy (`src/lib/founderContent.ts`) avoids: guaranteed
employment/cooperation, equity, code rights, revenue rights, unlimited creator access,
24/7 support, and a guaranteed exact pre-launch date. It uses "priority consideration,"
"subject to scheduling and availability," "early access to development builds as they
become available," and states plainly that a purchase doesn't guarantee employment or
cooperation and that final product decisions remain with RentYourTime. The same points
are restated in `/terms#founder-program`. Always "Founder," never "Funder."

## Translations

No localization system exists anywhere in this repository (checked before building
this — no `next-intl`/`react-i18next`/equivalent, no locale routing). Per the brief's
own condition ("add Polish only if the repo already has a localization system"), this
ships English-only. Content is still kept out of JSX, in `src/lib/founderContent.ts`
(matching how `Pricing.tsx`/`Privacy.tsx`/`Terms.tsx` already extract their copy into
local data) — so adding a real i18n layer later is a data-file problem, not a rewrite.

## Environment variables

```
STRIPE_FOUNDER_FIRST_PRICE_ID=price_...
STRIPE_FOUNDER_GOLD_PRICE_ID=price_...
STRIPE_FOUNDER_BLACK_PRICE_ID=price_...
```

Reuses the existing `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `APP_URL`. See
`.env.example`.

## Migrations

No separate migration command — the four tables are created automatically the first
time `getDb()` runs after deploying (same as every other table in this project). Safe
on a live database: `CREATE TABLE IF NOT EXISTS` is a no-op if already applied, and
nothing existing is dropped, renamed, or rewritten.

## Seeding the tiers

```bash
npm run founders:seed
```

Runs `scripts/seed-founder-tiers.mjs` — upserts the three tiers by `slug`, safe to
re-run any time (updates name/price/Stripe Price ID/early-access days, but **never**
touches `sold_quantity`, and never touches `total_quantity` on an existing row, so it
can't silently change a limit under real buyers). Reads
`STRIPE_FOUNDER_{FIRST,GOLD,BLACK}_PRICE_ID` from the environment if present.

## Stripe Dashboard setup

1. Create three **one-time** Prices (not recurring) in USD: $50.00, $125.00, $1,899.00.
   Product name suggestion: "RentYourTime Founder — <tier name>".
2. Put each Price ID into `STRIPE_FOUNDER_*_PRICE_ID` and re-run
   `npm run founders:seed` (or update the row directly — the seed script is
   idempotent either way).
3. Webhook: open the **existing** endpoint (the same one already receiving
   `checkout.session.completed` for Pro and Contributions) — no new event types are
   needed; see [`docs/STRIPE.md`](./STRIPE.md).

- `tests/lib/founders.test.ts` — availability math, number-padding, tier-limit
  guard, atomic number assignment (including the "more buyers than slots settle"
  edge case and idempotent replay), `getActiveFounderPurchase`.
- `tests/lib/subscriptions.test.ts` ("grantFounderPro") — the Pro-grant merge matrix,

- `tests/api/founders-webhook.test.ts` — settlement, number assignment, Pro grant,
  amount-mismatch refusal, duplicate-event idempotency (including "no double
  decrement" across two distinct event ids for the same purchase), refund, and the
  Stripe-subscriber-safety regression test at the webhook level too.
- `tests/api/admin-founders.test.ts` — admin gate (401/403), tier activate/deactivate,
  limit-below-sold rejection, purchases list, Founder Black kit status + tracking.
- For manual end-to-end testing: `stripe listen --forward-to localhost:3000/api/webhook`,
  then buy a tier with a [Stripe test card](https://stripe.com/docs/testing#cards)
  (`4242 4242 4242 4242`, any future expiry/CVC).

## Known limitations

- Discord role assignment is not implemented — see "Discord" above.
- Refunding a Founder purchase does not automatically revoke previously-granted Pro
  access — see "How Pro is granted" above.
- The extreme "tier sells out in the exact instant this purchase settles" race leaves
  a `PAID` purchase with no `founder_number`, needing manual admin resolution.
- No public Founders Directory page renders `consent_directory` yet — the consent
  itself is fully wired, the listing page is a follow-up.
- English only (no localization system exists in this repo to plug into).
